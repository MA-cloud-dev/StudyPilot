# StudyPilot V1 需求文档

## 1. 项目概述

### 1.1 当前仓库同步状态

- 同步日期: `2026-03-31`
- 本文档仍然描述 **V1 目标需求**，不是当前功能完成度清单
- 当前仓库已完成阶段 1 与阶段 2:
  - 正式前后端工程骨架、契约、状态机、核心类型与测试基线已建立
  - 后端已具备真实的资料解析、切片、检索、计划生成、学习会话、测试评分与工作流推进最小闭环
  - 前端已完成首页、计划中心、学习工作台、知识仓库、阶段测试、个人主页六个正式路由的真实闭环接线
  - 当前前端已支持建档、上传资料、生成计划、发起学习、提交测试与查看结果
- 当前仓库仍未满足本文中的完整产品需求:
  - 默认仍使用 fake provider，真实外部模型接入未作为默认运行模式
  - 个性化、动态调参、流式学习体验仍处于后续阶段目标
- 因此阅读本文时，应将其视为**阶段 3 及之后的产品能力说明**

StudyPilot 是一个面向个人学习者的 AI 学习辅助 Web 应用。产品围绕学习全过程中的三个核心阶段展开:

1. 计划: 基于用户目标、已有基础、时间预算和知识仓库资料，生成贴近个人情况的长期与短期学习计划。
2. 输入: 基于当前微观计划、知识仓库内容和用户学习偏好，生成定制化学习内容，并支持连续对话式学习。
3. 输出: 以测试驱动学习，在每个关键学习节点后生成适量、难度合适的测试题，并根据结果更新后续学习安排。

产品目标不是提供一个通用聊天机器人，而是提供一个能够围绕学习任务持续行动、自动切换阶段、逐步理解用户习惯的学习 Agent。

## 2. 产品目标

### 2.1 产品愿景

构建一个测试驱动学习的 AI 学习辅助系统，让用户能够围绕某一学习主题完成从目标设定、计划生成、内容学习、阶段检验到持续迭代的完整闭环。

### 2.2 核心目标

- 为单个用户提供一套完整的学习闭环，而不是碎片化问答能力。
- 生成同时包含宏观周期安排和微观执行安排的学习计划。
- 在学习过程中提供“沉浸式阅读 + 侧边栏AI答疑”的交互体验，提升学习效率。
- 在每次学习后提供可操作的测试和反馈，包含如“我不确定”等兜底选项以精准评估掌握度。
- 让系统可以在多轮使用中逐渐学习用户偏好，实现长期个性化。

### 2.3 核心用户价值

- 自动生成贴合个人情况的学习计划，而不是模板化任务列表。
- 自动整理知识点、示例、解释和补充说明，降低用户自行筛选资料的成本。
- 通过贯穿全程的测试机制帮助用户检查掌握情况、促进知识内化。
- 随着使用积累，系统对用户的讲解方式和出题风格越来越贴合。

## 3. 目标用户与典型场景

### 3.1 目标用户

V1 面向单用户 MVP，主要用户为有明确学习目标、需要计划与反馈支持的自学者。

### 3.2 典型场景

- 用户希望系统根据自己的目标和已有资料，制定一周到一月的学习总计划。
- 用户希望系统把今天或当前一小时的学习内容拆解清楚，明确学什么、学多久、达到什么程度。
- 用户在学习过程中持续提问，希望系统以自己偏好的风格讲解知识点。
- 用户在完成某个小节或阶段后，希望系统自动发起测试来检验成果。
- 用户希望系统根据最近测试结果，自动调整后续计划和题目难度。

## 4. 核心业务闭环

StudyPilot 的核心业务流程为:

1. 用户建立学习档案，说明目标、时间、基础和偏好。
2. 用户上传学习资料、讲义、笔记等，形成个人知识仓库。
3. 系统生成宏观计划和当前阶段的微观计划。
4. 系统依据微观计划输出当前学习内容，并与用户持续对话学习。
5. 当达到计划中的测试触发条件后，系统自动生成阶段测试。
6. 系统根据用户作答情况进行评分、讲评和掌握度判断。
7. 系统回写偏好、掌握度和学习历史，更新后续学习安排，进入下一轮循环。

## 5. 功能需求

## 5.1 用户建档与偏好初始化

系统应支持用户在首次使用时建立基础学习档案，至少包括:

- 当前学习主题或目标
- 目标周期
- 每日或每周可投入时间
- 当前基础水平的自我评估
- 偏好的讲解风格
- 偏好的题目风格和难度

系统应允许用户在后续使用中不断修正这些信息，并基于行为和对话自动补充偏好画像。

## 5.2 知识仓库模块

知识仓库是系统的重要输入来源，既服务于用户阅读，也服务于 Agent 分析。

### 5.2.1 资料输入要求

- 支持用户上传个人学习资料、讲义、教材摘录、笔记等内容。
- V1 优先支持 PDF、Markdown、纯文本、常见笔记类文档（如 .md、.txt、.pdf）。
- 系统需要对资料进行解析、切分、标记和检索，以便后续 Agent 使用。

#### 文件约束

- 单个文件大小上限为 **20 MB**。
- 每次上传文件数量上限为 **10 个**。
- 单用户知识仓库总容量上限为 **500 MB**（V1 阶段）。
- 超出限制时，系统应在上传前给出明确提示，不得静默截断。

#### 解析失败处理

- 系统在文件解析失败时，应向用户显示具体失败原因（如格式不支持、文件损坏、内容为空）。
- 解析失败的资料不会进入检索索引，但仍应保留上传记录，供用户重新上传或删除。
- 系统应支持对解析失败的文件执行一次自动重试；重试后仍失败则标记为永久失败状态。
- 解析失败不应阻塞其他已上传资料的正常使用。

### 5.2.2 资料组织与关联

- 知识仓库中的资料在 V1 阶段为用户全局共享，不与特定计划绑定。
- 系统应支持用户为资料附加标签，以便在多个学习主题下复用。
- 计划生成时，Agent 应优先参考与当前学习主题关键词相关的资料，而非全量加载所有内容。
- 资料删除后，已生成的计划和学习内容不受影响，但后续 Agent 检索将不再引用该资料。

### 5.2.3 资料使用要求

- 计划模块可以根据知识仓库内容判断学习主题结构和材料覆盖情况。
- 输入模块可以根据知识仓库抽取知识点、示例和术语解释。
- 输出模块可以根据知识仓库和已学内容生成更贴合资料范围的测试题目。
- 当知识仓库为空时，Agent 应能够仅凭用户目标和基础信息生成计划，并提示用户上传资料可提升质量。

## 5.3 计划模块

计划模块负责学习路径设计，是整个系统的起点。

### 5.3.1 宏观计划

宏观计划面向较长周期，通常是一周、一个月或更长时间。宏观计划应满足以下要求:

- 描述整体学习路径和阶段目标。
- 说明每个阶段大致需要覆盖哪些主题或模块。
- 体现时间安排、优先级和阶段性里程碑。
- 不要求精确到每一次学习活动，但需要清楚反映总体推进路线。

### 5.3.2 微观计划

微观计划面向单日、单次学习时段或较短执行周期，应尽可能细化。微观计划在工作台首页以“今日任务列表”形式呈现，应包括:

- 本次学习的具体主题、章节或知识点
- 预计学习时长
- 建议的学习顺序与完成状态（待学习、已完成）
- 每一部分预期达到的理解程度
- 本次学习结束后的测试触发点

微观计划应能直接驱动输入模块和输出模块执行，属于真正可落地的行动计划。

### 5.3.3 计划生成原则与交互交互

- **对话式生成**：用户可通过独立的“创建新计划 (AI)”对话框，用自然语言提供目标，并直接在对话栏中上传相关资料。
- 必须结合用户目标、基础、时间约束与知识仓库资料综合生成。
- 同一用户的计划应明显体现个体差异，而不是固定模板。
- 计划需要支持根据学习结果和测试结果动态调整。

## 5.4 输入模块

输入模块是辅助学习阶段的核心，负责把微观计划转化为适合用户学习的内容。

### 5.4.1 内容生成要求与交互布局

- 基于当前微观计划、知识仓库内容和用户即时要求生成学习内容。
- **双栏交互界面**：系统左侧展示结构化、可读的教科书式讲义正文；右侧为“学习助手”AI对话窗口，支持用户在阅读时随时提问。
- 内容应覆盖定义、原理、例子、重点、易错点、应用场景等必要元素。
- 当用户提出更具体要求时，系统应支持在右侧侧边栏中重讲、举例或答疑，而不打断用户的左侧主线阅读体验。

### 5.4.2 个性化要求

系统需要支持根据用户偏好提供定制化讲解，包括但不限于:

- 严谨、专业、信息密度高的讲解方式
- 有趣、形象、轻松、容易理解的讲解方式
- 更偏概念理解或更偏应用实战的内容组织
- 更偏定义推导或更偏案例说明的表达风格

### 5.4.3 持续学习用户习惯

系统需要具备通过以下信号持续理解用户的能力:

- 用户显式填写的偏好
- 用户在对话中的即时要求
- 用户对内容难度、长度、节奏的反馈
- 用户在测试中的表现和错题类型

## 5.5 输出模块

输出模块以测试为中心，是整个产品的关键模块。

### 5.5.1 测试目标

- 客观检验用户对学习内容的掌握程度
- 通过测试过程促进知识回忆、迁移和内化
- 为后续计划和讲解决策提供反馈依据

### 5.5.2 测试层级

系统需要支持至少三个层级的测试:

- 小节测试: 用户完成一次微观学习任务后触发
- 单元测试: 用户完成某个阶段性模块后触发
- 总测试: 用户完成整个学习周期或完整主题后触发

### 5.5.3 测试设计要求与交互细节

- 测试内容必须与近期学习内容和知识仓库范围相关。
- 题目应单题流式呈现。交互上除“提交答案”外，必须提供“我不确定（跳过）”功能，用于避免用户盲猜并捕捉其真实的知识盲区。
- 题目难度应适中，对用户具有一定挑战但不应过度挫败。
- 题目风格可根据用户偏好做个性化调整。
- 测试后必须给出评分、讲评、错误分析和改进建议。

### 5.5.4 测试触发要求

- 测试不依赖用户主动选择，而应根据学习状态自动触发。
- 系统应根据计划节点、学习完成度和阶段边界决定何时发起测试。

## 5.6 Agent 自动调度

系统需要具备基于当前状态自动调用不同 Agent 的能力，用户不需要手动切换角色。

### 5.6.1 角色划分

- `plan_agent`: 负责生成与调整宏观计划和微观计划
- `input_agent`: 负责生成学习内容并进行互动讲解
- `output_agent`: 负责生成测试、评分、讲评和后续建议
- `supervisor_agent`: 负责判断当前阶段并在三个子 Agent 之间切换

### 5.6.2 调度原则与可视菜单

- 优先由系统（`supervisor_agent`）判断当前用户处于哪个学习阶段并流转。
- **全局菜单补充**：虽然强调自动调度，但左侧固定导航栏需提供`全部学习计划`、`学习工作台`、`知识仓库`、`阶段测试`、`个人主页`等入口，允许用户随时切换查看历史和库，并在工作台中自动回归当前正处于的学习节点。
- 在同一用户学习会话中保留必要上下文，避免频繁丢失状态
- 允许根据测试结果回退到补学阶段，再重新进入测试

## 5.7 学习记录与可追溯性

系统应保存和展示用户的关键学习历史，包括:

- 已生成的计划版本
- 已完成和未完成的微观计划
- 学习会话记录和阶段摘要
- 历史测试结果、错题与讲评
- 用户偏好变化和掌握度变化

这些记录既要服务用户复盘，也要服务系统后续决策。

## 6. MVP 范围与非目标

### 6.1 V1 范围

- 单用户 Web 应用
- 本地上传知识仓库
- AI 自动生成计划、学习内容和测试
- 总控 Agent 调度三个子 Agent
- 基本的学习历史、计划状态和测试结果持久化

### 6.2 V1 暂不覆盖内容

- 多用户协作与组织空间
- 复杂账号权限体系
- 教师端、管理端或课程运营后台
- 社交化学习功能
- 外部网页抓取与公开课程平台集成
- 高复杂度自适应推荐算法

## 7. 非功能需求

### 7.1 稳定性

- 系统在计划生成、内容生成、测试生成等关键环节应具备稳定响应能力。
- 出现失败时应可追踪并具备可恢复机制。

### 7.2 可追踪性

- 系统需要记录当前学习阶段、Agent 调用结果和关键状态变更。
- 用户可以看到当前计划执行到了哪里，为什么进入测试或回退补学。

### 7.3 可扩展性

- 系统设计应为未来支持多用户、多学科优化和更多 Agent 能力保留扩展空间。

### 7.4 持久化

- 用户资料、计划、学习记录、测试结果和偏好画像应持久保存。

## 8. V1 成功标准

如果满足以下条件，则可认为 V1 达到基本目标:

- 系统可以根据用户目标和知识仓库生成一份可执行的宏观计划和微观计划。
- 系统可以依据微观计划生成结构化、可持续互动的学习内容。
- 系统可以在学习节点自动发起测试，并输出评分、讲评和下一步建议。
- 系统可以记录用户偏好，并在后续计划、讲解和出题中体现个性化差异。
- 用户无需手动切换模块，即可完成一次完整的学习闭环。

## 9. 文档假设

- 第一版以单用户完整学习闭环为主，不引入复杂账号体系。
- 第一版支持通用学科框架，但预留按学科细化的扩展空间。
- 知识仓库以用户主动上传资料为主，不包含外部内容抓取。
- 规格实现阶段不会提前锁死具体模型供应商或底层框架。
