# StudyPilot V1 技术选型文档

## 1. 文档目标

本文档用于明确 StudyPilot V1 的技术选型、选择理由、备选方案取舍和后续替换边界。

本文档回答的核心问题不是“系统要做什么”，而是“为什么用这套技术来实现它”。业务需求请参考 `requirement.md`，系统规格请参考 `spec.md`。

### 1.1 当前仓库同步状态

- 同步日期: `2026-03-31`
- 当前仓库已经按本文件推荐路线落地阶段 1 后端内核最小闭环，并完成阶段 2 前端正式工程对接与阶段 3 纵向联调验收:
  - 前端: Next.js App Router + React + TypeScript + Tailwind CSS + TanStack Query
  - 后端: FastAPI + Pydantic Settings + SQLAlchemy 2 + Alembic
  - 契约: 由后端导出 `OpenAPI`，前端生成类型消费
  - 部署骨架: 提供 `docker-compose.yml` 与 Dockerfile
  - 后端内核: 已接入 `LangGraph`、`OpenAI-compatible Adapter` 边界、`pypdf` 解析和最小混合检索
  - 前端正式页: 已完成首页、profile、knowledge、plans、workbench、assessments 的真实接口接线

  - 当前前端采用页面局部状态保存学习会话与测试作答过程；学习会话尚未做刷新恢复

## 2. 选型原则

StudyPilot V1 的技术选型遵循以下原则:

- 单用户 MVP 优先，先打通完整学习闭环，不为未来假想复杂度过度设计。
- AI-first，技术栈应优先服务 Agent 编排、文档解析、检索、结构化输出和流式交互。
- 状态可追踪，系统必须明确知道当前处于计划、学习、测试还是补学阶段。
- 统一上下文，计划、学习、测试三个模块应共享用户画像、知识仓库和阶段状态。
- 避免过早拆服务，在 V1 阶段优先保证系统简单、稳定、可调试。
- 关键能力可替换，模型厂商、检索实现和异步执行层应保留替换空间。

## 3. 推荐技术栈总览

StudyPilot V1 的推荐技术栈如下:

- 前端: `Next.js App Router + React + TypeScript + Tailwind CSS + TanStack Query`
- 后端: `Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic`
- 数据库: `PostgreSQL + jsonb + pgvector`
- Agent 编排: `LangGraph`
- LLM 接入: 以 OpenAI 接口为默认适配面，通过 `LLMProviderAdapter` 接入不同模型厂商
- 检索层: 文档解析 + 切片 + 向量检索 + 元数据过滤
- 文件存储: V1 先采用本地文件存储或对象存储兼容抽象
- 异步任务: V1 初期轻量化后台任务，后续按需要补 Redis/Worker
- 部署: 单仓库开发，前后端分目录，Docker Compose 起本地环境

## 4. 前端技术选型

## 4.1 推荐方案

推荐使用:

- `Next.js App Router`
- `React`
- `TypeScript`
- `Tailwind CSS`
- `TanStack Query`

## 4.2 选择理由

### Next.js App Router

StudyPilot 的前端不是普通后台管理页，而是一个包含以下特征的学习工作台:

- 宏观计划中心
- 沉浸式学习工作台
- 右侧持续对话答疑
- 资料上传与解析状态展示
- 阶段测试与结果回看

这类产品既有强交互页面，也有服务端数据拉取和流式内容输出的需求。Next.js App Router 比纯静态原型更适合承载真实产品工程，原因包括:

- 适合构建多页面产品结构，而不是只做前端演示稿
- 能自然支持服务端渲染、流式响应和渐进式页面加载
- 与 React 生态兼容，后续组件沉淀和状态管理更顺畅
- 更适合承接后续登录、文件上传、服务端动作等产品化能力

### TypeScript

StudyPilot 的前端会承接大量结构化对象，包括计划、学习会话、测试结果和资料元数据。使用 TypeScript 可以:

- 让前后端的领域对象边界更清晰
- 减少界面层因字段变化导致的错误
- 提升计划、测试、知识仓库等复杂页面的可维护性

### Tailwind CSS

当前仓库中的 `FrontendDesign` 已经有静态原型，说明项目对界面结构和节奏有较强要求。Tailwind CSS 适合在保留设计意图的前提下快速把原型落成组件系统:

- 适合快节奏搭建产品 UI
- 容易抽象学习卡片、计划列表、双栏布局、测试卡片等可复用组件
- 后续可以和 design token 或 UI 组件库结合

### TanStack Query

StudyPilot 的前端核心状态大多来自服务端，例如:

- 当前宏观计划和微观计划
- 当前学习会话
- 当前测试题和测试结果
- 资料解析状态
- 当前工作流状态

这些都属于服务端状态，不适合被简单塞入本地全局状态库。TanStack Query 适合:

- 获取和缓存服务端状态
- 处理计划生成、测试提交等 mutation
- 处理资料上传后的轮询、状态刷新和错误恢复

当前实现补充:

- 已统一 query key、错误归一化与 mutation 成功后的显式失效刷新
- 测试详情读取已补齐，可通过 `assessment_id` 在刷新后恢复待答题题面

## 4.3 为什么不继续使用纯静态原型

当前 `FrontendDesign` 更适合作为交互原型和视觉参考，而不是正式工程基础。原因包括:

- 纯 HTML/CSS/JS 原型适合展示交互，不适合承载复杂业务状态
- 后续对计划、对话、测试和知识仓库的联动会迅速增加维护成本
- 流式学习内容、测试状态回退、资料解析轮询等能力更适合框架化实现

## 4.4 为什么当前不优先选择 Vue/Nuxt

Vue/Nuxt 并不是错误方案，但当前不优先推荐，原因是:

- 项目当前没有既有 Vue 技术资产约束
- React 生态在 AI UI、流式渲染、组件沉淀方面更通用
- 如果后续需要更多 AI 交互式组件和社区方案，React 侧选择更多

换句话说，Vue/Nuxt 可以做，但在没有团队或历史包袱的前提下，Next.js + React 更稳妥。

## 5. 后端技术选型

## 5.1 推荐方案

推荐使用:

- `Python 3.12`
- `FastAPI`
- `Pydantic v2`
- `SQLAlchemy 2`
- `Alembic`

当前实现补充:

- 已新增 `langgraph`、`openai`、`pypdf`
- 已实现 `LLMProviderAdapter`、`RetrievalProvider`、解析/切片/评分服务边界

## 5.2 为什么选择 Python

StudyPilot 的核心能力不在传统业务 CRUD，而在以下 AI 相关能力:

- 文档解析
- 检索增强
- Agent 编排
- 结构化输出
- 自动评分
- 学习过程总结

这些能力的成熟库和工程实践在 Python 生态中更丰富。使用 Python 可以降低以下成本:

- 大模型对接成本
- 向量检索和文本处理成本
- Agent 原型验证成本
- 文档解析和评估链路搭建成本

## 5.3 为什么选择 FastAPI，而不是 Spring Boot

Spring Boot 是优秀的传统后端框架，但对 StudyPilot 这类 AI 产品而言，FastAPI 更合适。

原因如下:

### 1. 项目重心更偏 AI 系统，而不是传统企业业务系统

StudyPilot 更像“Agent 驱动的学习系统”，其核心工作是:

- 调用大模型
- 处理知识仓库
- 协调 Agent 节点
- 维护工作流状态
- 输出结构化计划和测试结果

这类业务与 Python 生态天然更贴近。

### 2. FastAPI 与类型化数据模型配合更自然

本项目有大量结构化对象:

- `UserProfile`
- `MacroPlan`
- `MicroPlan`
- `Assessment`
- `Evaluation`
- `AgentDecision`

FastAPI 与 Pydantic 的组合非常适合将这些对象直接映射为 API 输入输出和内部约束模型。

### 3. 流式接口和 AI 调用场景更轻便

输入模块需要持续对话、流式讲解和即时反馈，FastAPI 在构建这类 API 时更轻量，试验成本更低。

### 4. AI 生态整合成本更低

无论是 LangGraph、向量检索组件、文档切片工具，还是后续的模型评估工具，Python 集成路径通常更短。

### 5. V1 更需要快速验证，而不是先建立重型工程体系

Spring Boot 的强项在成熟企业后端体系、组织协作和重型平台治理。但在当前阶段，StudyPilot 更需要快速打通计划、学习、测试闭环，因此 FastAPI 更贴身。

结论是:

- 如果团队未来明确以 Java 为主、已有成熟基础设施，也可以在后期评估迁移或混合架构。
- 但对于当前 V1，FastAPI 是更优默认值。

## 6. 数据库技术选型

## 6.1 推荐方案

推荐使用:

- `PostgreSQL`
- `jsonb`
- `pgvector`

当前实现补充:

- 为兼容自动化测试，当前 `KnowledgeChunk.embedding` 先以 JSON 数组落库
- 后续切换到 PostgreSQL 生产环境时，再进一步映射到 `pgvector`

## 6.2 为什么选择 PostgreSQL，而不是 MySQL

StudyPilot 的数据不是单纯的用户表、订单表、关系表，而包含大量半结构化和 AI 相关数据，例如:

- 用户偏好快照
- Agent 决策记录
- 计划版本历史
- 测试讲评结果
- 资料切片元数据

PostgreSQL 更适合这一类数据，理由如下:

### 1. 对半结构化数据更友好

`jsonb` 很适合保存不完全固定但又需要查询和索引的数据，例如计划快照、评语、偏好摘要。

### 2. 更适合 AI 检索场景

StudyPilot 的知识仓库需要支持:

- 向量检索
- 元数据过滤
- 关键词或全文检索

PostgreSQL 配合 `pgvector` 和自身的检索能力，可以在 V1 阶段用一套数据库同时承接业务数据和检索数据。

### 3. 状态型系统更受益于更强的表达能力

本项目会持续记录计划版本、状态流转和 Agent 决策。PostgreSQL 更适合处理复杂查询、版本记录和结构混合的数据模式。

### 4. 有利于降低 V1 的系统复杂度

如果一开始就拆成“业务数据库 + 向量数据库 + 日志系统”，会显著提高工程复杂度。PostgreSQL 可以帮助 V1 先把核心链路收敛到一个主存储。

## 6.3 为什么当前不优先选择 MySQL

MySQL 当然可以承载常规业务数据，但在 StudyPilot 里它不是最优默认值，主要因为:

- 对半结构化数据和复杂检索组合的工程体验通常不如 PostgreSQL
- 与 AI 检索链路的集成灵活性不如 PostgreSQL 方案直接
- 更容易让系统走向“传统业务库 + 外挂检索系统”的早期拆分

结论不是 MySQL 不能做，而是 PostgreSQL 更贴合 StudyPilot 当前的数据形态。

## 7. Agent 技术选型

## 7.1 推荐方案

推荐使用:

- `LangGraph` 作为主编排层
- `LangChain` 按需作为组件层使用

当前实现补充:

- 已落地最小 `supervisor -> specialist` 图结构
- 当前由代码控制阶段切换，节点内内容生成与评分通过 provider 调用

## 7.2 为什么选择 LangGraph，而不是把 LangChain 作为主框架

关键点不是“LangGraph 比 LangChain 更高级”，而是两者定位不同:

- `LangChain` 更像组件与能力层，适合模型封装、检索组件、工具封装和快速链路搭建
- `LangGraph` 更像有状态工作流编排层，适合构建长时运行、可追踪、可回退的 Agent 系统

StudyPilot 的核心不是一个会聊天的 Agent，而是一个显式状态机驱动的学习系统。系统至少需要管理以下状态:

- `planning`
- `learning`
- `checkpoint_test`
- `unit_review`
- `unit_test`
- `final_review`
- `final_test`
- `next_cycle`

这正是 LangGraph 更适合的原因。

### 1. StudyPilot 是状态机问题，不只是提示词问题

你定义的 `supervisor_agent` 需要根据当前状态、计划节点、测试结果和掌握度决定下一步进入哪里。这种逻辑更适合由状态图和条件路由来管理，而不是由一个高自由度 Agent 自己决定所有流程。

### 2. 需要可追踪和可恢复

学习系统不能只输出一句结果，还要解释:

- 为什么现在发起测试
- 为什么进入补学
- 为什么调整计划

LangGraph 更适合把这些决策显式沉淀在工作流状态中。

### 3. 需要“代码控制流程，模型负责节点内推理”

StudyPilot 最合理的设计是:

- 流程切换由代码和状态机控制
- 计划生成、讲解生成、测试生成、评分讲评等节点内部再调用大模型

LangGraph 更适合这种模式。

### 4. 更符合总控 + 3 子 Agent 的产品架构

在本项目中:

- `supervisor` 负责阶段判断与路由
- `plan_agent` 负责结构化计划生成
- `input_agent` 负责学习内容与对话
- `output_agent` 负责测试与评分

这四者之间更像图中的节点协作，而不是多个完全自治的聊天 Agent。

## 7.3 LangGraph 与 LangChain 的关系

推荐理解方式如下:

- `LangGraph` 负责流程编排和状态流转
- `LangChain` 可以只用其中需要的组件，例如 prompt 封装、检索封装或模型调用包装

因此本项目不是“二选一完全排斥”，而是:

- 不把 LangChain 当主编排框架
- 允许把 LangChain 当组件工具层使用

## 8. 大模型接入策略

## 8.1 推荐方案

推荐采用:

- 以 OpenAI 风格接口作为默认对接面
- 在业务层与具体模型厂商之间增加 `LLMProviderAdapter`

## 8.2 为什么以 OpenAI 风格接口作为默认适配面

原因包括:

- 工具生态广，便于先打通 V1
- 大量模型服务提供方会提供兼容 OpenAI 的调用方式
- 有利于在不改业务层的前提下切换模型厂商

## 8.3 OpenAI-compatible 不等于完全等价

这是非常重要的工程前提。

虽然许多模型平台宣称兼容 OpenAI 接口，但兼容的通常只是“调用形态”，不一定完全等价于所有能力。例如不同厂商可能在以下方面存在差异:

- 是否支持结构化输出
- 是否支持工具调用
- 是否支持流式输出
- 是否支持文件处理
- 是否支持长上下文
- 是否支持同样的错误码和返回字段

因此，不能假设“只要兼容 OpenAI 就一定无缝替换”。

## 8.4 阿里百炼这类平台如何看待

像阿里百炼这类提供 OpenAI 兼容调用方式的平台，原则上可以接入 StudyPilot。

但正确做法不是在业务代码中直接写死某一家厂商的接口细节，而是通过 `LLMProviderAdapter` 做一层能力适配。这样即使不同厂商在结构化输出、工具调用或返回格式上有差异，也不会污染计划、学习和测试模块本身。

## 9. 基础设施建议

## 9.1 文件存储

V1 建议:

- 本地开发阶段使用本地文件目录存储原始资料
- 生产阶段保留切换到对象存储的能力

关键要求:

- 文件路径不要直接暴露给业务层
- 统一通过文件存储抽象访问原始资料

## 9.2 检索层

知识仓库建议采用统一检索入口，内部组合:

- 文档解析
- 文本切片
- 向量检索
- 元数据过滤
- 可选关键词检索

这样计划模块、输入模块和输出模块都从同一个检索入口取上下文，避免三套实现。

## 9.3 异步任务

V1 建议:

- 先让轻量任务由应用服务直接处理
- 将文档解析、切片、embedding、长耗时测试生成纳入后台任务
- 等吞吐量上来后，再引入更完整的队列和 worker 体系

当前实现补充:

- 阶段 1 仍采用同步执行
- 服务边界已经拆出，便于后续迁移到异步任务

## 9.4 部署方式

推荐:

- 单仓库
- 前后端分目录
- 本地通过 Docker Compose 启动

这样既方便开发，也方便在后续扩展为独立部署。

## 10. 模块到技术映射

## 10.1 计划模块

实现映射:

- `plan_agent`
- `RetrievalProvider`
- 结构化输出能力
- `MacroPlan` / `MicroPlan` 持久化

实现方式:

- 读取用户画像、目标、时间预算和知识仓库资料
- 从检索层获取相关课程结构和资料上下文
- 调用模型输出结构化计划
- 存档计划版本，供后续学习和测试调用

## 10.2 输入模块

实现映射:

- `input_agent`
- 流式接口
- 偏好画像读取
- 学习会话状态更新

实现方式:

- 读取当前微观计划与已解析知识片段
- 根据显式偏好和隐式偏好生成讲解内容
- 支持用户继续追问
- 将会话摘要和掌握度信号回写到 `LearningSession`

## 10.3 输出模块

实现映射:

- `output_agent`
- 评分器
- 测试结果持久化
- 状态回退逻辑

实现方式:

- 根据已学范围、最近表现和偏好生成适量测试题
- 对用户答案进行自动评分和讲评
- 将结果映射回知识点、错因和补学建议
- 当掌握度不足时，驱动工作流回退到学习或复盘状态

## 10.4 总控模块

实现映射:

- `supervisor`
- `WorkflowState`
- 条件路由
- 决策日志

实现方式:

- 读取当前阶段、计划进度、学习摘要和最近测试结果
- 判断下一步是继续学习、进入测试还是回退补学
- 生成 `AgentTask` 和 `AgentDecision`
- 更新工作流状态

## 11. 关键接口与类型边界

以下类型是技术设计中的关键边界，建议在实现中保持明确:

- `WorkflowState`: 当前阶段、当前计划节点、最近测试结果、下一步动作
- `UserProfile`: 用户目标、基础水平、偏好和行为总结
- `KnowledgeAsset`: 资料元数据、解析状态、切片引用和标签
- `MacroPlan`: 周期级计划
- `MicroPlan`: 执行级计划
- `LearningSession`: 学习会话、摘要、掌握度信号和完成度信号
- `Assessment`: 测试定义、题目范围、难度和状态
- `Evaluation`: 评分、讲评、错因和建议
- `LLMProviderAdapter`: 屏蔽底层模型厂商差异的统一调用接口
- `RetrievalProvider`: 屏蔽向量检索、关键词检索和元数据过滤差异的统一入口

这些类型应成为前后端、Agent 层和数据层之间的公共契约，而不是散落在各模块内部的隐式对象。

## 12. 替换边界与演进路径

## 12.1 当前推荐默认值

V1 当前推荐默认值如下:

- 前端: Next.js + React + TypeScript
- 后端: FastAPI + Python
- 数据库: PostgreSQL
- Agent 编排: LangGraph
- 模型接入面: OpenAI 风格接口 + Provider Adapter

## 12.2 后续可替换项

以下能力在未来可以替换，但不应影响业务层的核心设计:

- 模型厂商: 通过 `LLMProviderAdapter` 替换
- 检索实现: 通过 `RetrievalProvider` 替换
- 文件存储: 通过存储抽象替换
- 异步执行层: 从轻量后台任务演进到 Redis/Worker 或消息队列体系

## 12.3 当前不建议过早引入的内容

在 V1 阶段不建议优先引入:

- 微服务拆分
- 独立向量数据库
- 复杂事件总线
- 多模型路由优化平台
- 过重的企业级基础设施

原因不是这些方案不好，而是会削弱 V1 打通学习闭环的速度和调试效率。

## 13. 最终结论

StudyPilot 的本质不是一个普通问答机器人，也不是一个传统企业业务系统，而是一个围绕学习流程持续运行的状态化 Agent 产品。

因此，最优技术路线应当优先满足以下能力:

- 学习阶段可控
- Agent 调度可追踪
- 资料检索可复用
- 模型输出可结构化
- 前端交互可流式
- 后续模型与检索实现可替换

在当前阶段，`Next.js + FastAPI + PostgreSQL + LangGraph + OpenAI-compatible Adapter` 是最匹配 StudyPilot V1 目标的默认组合。
