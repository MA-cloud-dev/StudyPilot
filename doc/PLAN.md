## 2. 开发总原则

StudyPilot 的开发顺序不采用“只先后端”或“只先前端”的方式，而采用以下策略:

- 后端内核先行
- 前端骨架尽早跟进
- 核心能力按纵向切片联调

原因如下:

- 当前项目已经有静态前端原型，但真正决定产品成败的是后端闭环能力
- 如果先把前端做得很细，后期很可能因 Agent 和 API 变化频繁返工
- 如果只埋头做后端，则会延迟真实交互和产品可用性的验证

默认节奏应为:

`先打后端基础和契约 -> 立即起前端正式工程 -> 用 1 条完整业务切片做联调 -> 再扩第二层能力`

## 3. 阶段性开发计划

## 3.1 阶段 0：工程骨架与契约先行

目标:

- 建立正式项目结构
- 明确前后端分目录
- 明确环境变量、数据库连接、文档上传路径和基础运行方式
- 冻结第一批核心类型和 API 契约

第一批核心类型至少包括:

- `UserProfile`
- `KnowledgeAsset`
- `MacroPlan`
- `MicroPlan`
- `LearningSession`
- `Assessment`
- `Evaluation`
- `WorkflowState`

第一批接口分组至少包括:

- `/knowledge`
- `/plans`
- `/learning/session`
- `/assessments`
- `/workflow`

这一阶段的核心目标不是做功能，而是先把“项目怎么组织、数据怎么命名、接口怎么对接”定下来。

## 3.2 阶段 1：先做后端内核

目标:

- 搭建 FastAPI、PostgreSQL、文件存储和知识仓库解析链路
- 搭建 LangGraph 工作流骨架
- 搭建模型适配层
- 跑通第一批结构化输出

这一阶段不追求做完所有模块，而是要让后端能独立完成一条最小闭环:

- 用户建档
- 上传资料
- 生成宏观计划和微观计划
- 开启学习会话
- 生成小节测试

重点:

- 先把状态机和数据契约跑稳
- 先实现 `supervisor + 3 个 specialist 节点` 的最小编排
- 不提前追求复杂多 Agent 策略

当前状态:

- 已完成
- 当前实现采用同步解析与最小 LangGraph 编排
- 默认以 fake provider 保证本地测试与 CI 可稳定运行

## 3.3 阶段 2：前端正式工程尽快跟上

目标:

- 将 `FrontendDesign` 静态原型迁移到 Next.js 正式工程
- 完成应用壳层、路由、布局和核心页面骨架
- 对接已冻结的真实接口

优先完成的页面包括:

- 计划中心
- 学习工作台
- 知识仓库页
- 阶段测试页

这一阶段不做的重点:

- 不做大规模视觉精修
- 不在前端自行发明状态结构
- 不脱离后端契约独立扩展字段

当前状态:

- 已完成
- 当前仓库已完成最小建档入口与五个正式业务路由的真实契约对接
- 当前前端已接入共享 query key、统一错误归一化、mutation 失效刷新和通用数据状态组件
- 当前测试页已支持通过 `recent_assessment_id` 读取测试详情并在刷新后恢复待答题内容

## 3.4 阶段 3：按纵向切片联调

第一条业务切片固定为:

`用户建档 -> 上传资料 -> 生成计划 -> 进入学习 -> 提问一轮 -> 触发小节测试 -> 提交答案 -> 返回评分与补学建议`

这一阶段的目标是验证整个产品最关键的“计划 -> 输入 -> 输出”闭环。

联调原则:

- 不采用“各模块都做完再联调”的方式
- 优先围绕一条完整链路逐段打通
- 每打通一个节点，就验证一次状态流转是否正确

当前状态:

- 已完成
- 当前仓库已通过浏览器 E2E 打通 `建档 -> 上传资料 -> 生成计划 -> 学习 -> checkpoint -> 评分 -> unit_review / learning`
- 当前联调基线默认使用 fake provider，保证本地与 CI 可重复验证

## 3.5 阶段 4：闭环稳定后扩第二层能力

在第一条核心闭环稳定后，再扩展以下能力:

- 计划动态调整
- 单元测试
- 总测试
- 偏好自动总结
- 回退补学
- 知识仓库标签优化

这些能力都必须建立在第一条业务切片已经可用的前提上，不提前铺开。

当前状态:

- 已部分完成
- 已完成阶段 4A：主链路扩展
- 当前仓库已落地单元测试、总测试、review 推进、失败回退补学与最小动态调计划
- 当前后端已新增 workflow proceed 接口、assessment type / stage 一致性校验与阶段四 API / E2E 回归
- 当前前端已按 workflow 自动展示 checkpoint / unit / final / review 阶段，不再仅支持 checkpoint 测试
- 尚未完成阶段 4B / 4C：
  - 偏好自动总结
  - 知识仓库标签优化

## 4. Agent 实现顺序

Agent 的开发必须采用保守策略。

第一阶段只实现最小可用编排:

- `supervisor` 负责状态路由
- `plan_agent` 负责结构化计划生成
- `input_agent` 负责学习内容与答疑
- `output_agent` 负责测试与评分

实现原则:

- 流程切换优先由状态机控制
- 大模型主要负责节点内推理
- 先把状态、输入输出和可追踪性跑通
- 后续再逐步增强策略复杂度

## 5. 前后端并行边界

后端先交付:

- 核心类型定义
- API 契约
- mock 或真实接口
- 状态流转逻辑

前端只围绕已冻结契约进行对接:

- 不自行扩展后端字段
- 不自行定义计划或测试状态结构
- 所有字段变更必须先更新契约再更新界面

如果是单人开发:

- 严格按照阶段 0 -> 1 -> 2 -> 3 -> 4 串行推进

如果是 2 人以上小团队:

- 一人主后端与 Agent
- 一人主前端迁移与页面对接
- 两边都围绕同一条业务切片推进

## 6. 里程碑顺序

建议按如下里程碑推进:

1. 跑通项目骨架和核心类型
2. 跑通资料上传与解析
3. 跑通计划生成
4. 跑通学习会话和流式答疑
5. 跑通小节测试与评分
6. 打通完整联调切片
7. 再扩单元测试、总测试和动态调整

## 7. 验收标准

### 7.1 第一阶段验收

后端在没有正式前端的情况下，能通过接口或脚本完成以下最小闭环:

- 建档
- 上传资料
- 计划生成
- 学习会话
- 小节测试

当前结果:

- 已通过
- 当前仓库已具备端到端后端闭环测试，且无需人工改数据库或手动切状态

### 7.2 第二阶段验收

前端正式工程能够:

- 加载真实计划
- 展示学习内容
- 发起提问
- 展示测试题和结果

且不再依赖静态假数据。

当前结果:

- 已通过
- 当前前端已可围绕真实后端完成建档、上传资料、生成计划、进入学习、提交测试并展示结果

### 7.3 联调验收

从“用户上传一份资料”开始，到“系统返回一份计划并完成一次学习后测试”结束，全链路不需要人工改数据库或手动切状态。

当前结果:

- 已通过
- 当前仓库已提供浏览器 E2E happy path，可在独立测试栈中自动完成整条业务切片验证

### 7.4 回退验收

测试不达标时，`WorkflowState` 能正确回退到学习或复盘状态，而不是停留在测试页。

当前结果:

- 已通过
- 当前仓库已提供浏览器 E2E fallback path 与 API 集成测试，验证 checkpoint / unit_test 未达标时回退到 `learning`

### 7.6 第四阶段验收

阶段四主链路扩展完成后，系统至少应满足以下条件:

- checkpoint 通过后可以进入 `unit_review`
- `unit_review` 可推进到 `unit_test`
- `unit_test` 通过后可进入 `final_review`，失败时可回退补学
- `final_review` 可推进到 `final_test`
- `final_test` 通过后进入 `next_cycle`，失败时回退到 `learning`
- 回退时当前 `MicroPlan` 会根据最近评测结果进行最小补学调整

当前结果:

- 阶段 4A 已通过
- 当前仓库已通过 API 集成测试覆盖 `checkpoint -> unit_review -> unit_test -> final_review -> final_test -> next_cycle`
- 当前仓库已通过浏览器 E2E 覆盖阶段四 happy path 与 unit fallback path

### 7.5 文档与契约验收

实现中的 API 和类型命名必须与以下文档保持一致:

- `spec.md`
- `tech-stack.md`
- `PLAN.md`

前后端不得各自创造相互冲突的数据模型。

## 8. 当前前提假设

- 当前项目是单用户 MVP
- 已有静态前端原型，但没有正式工程骨架
- 技术路线默认采用 `Next.js + FastAPI + PostgreSQL + LangGraph`
- 当前阶段目标是尽快验证产品闭环
- “第一条完整业务切片打通”优先级高于页面精修和高级 Agent 策略

## 9. 结论

StudyPilot 的最佳开发顺序是:

- 先打工程骨架和数据契约
- 再优先完成后端内核
- 紧接着搭建前端正式工程并对接真实接口
- 然后通过一条完整业务切片完成联调验证
- 最后再扩展第二层能力

该顺序的目标不是最快做出界面，而是最快验证整个学习系统是否真正闭环可用。
